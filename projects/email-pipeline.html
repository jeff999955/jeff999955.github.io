TravoAI · MyProGuide · 2024

A serverless pipeline that handles booking cancellations

At TravoAI I helped MyProGuide stop processing cancellations by hand. Online travel agencies email a notice whenever a customer cancels; this pipeline reads those emails, works out which booking they're about, and updates the order, so the Ops team no longer does it one email at a time.

  • 1+ yearin production
  • 12travel agencies parsed

The problem

MyProGuide sells tours through many online travel agencies (OTAs) at once: Klook, KKday, Viator, GetYourGuide, Trip.com, Bokun, Rezio and others, across Taiwan, Thailand, Vietnam and Cambodia. When a customer cancels on one of them, the OTA sends an email. Someone on the Ops team had to open each one, find the booking and cancel it by hand. Every OTA formats its emails differently, often in several templates and languages.

How it works

  1. Each team gets its own inbox addressA random per-team address on the system domain. Ops sets up forwarding from each OTA account to it, so the address itself says which team the mail belongs to.
  2. AWS SES receives the emailA receipt rule hands every message to the pipeline.
  3. Filter Lambda checks the recipient (synchronous)It validates the address against the team API. This step runs synchronously because it decides whether anything else should run.Unknown recipient: dropped silently, no bounce
  4. The raw email is stored in S3Every accepted message is kept for audits and re-processing.
  5. Parse Lambda reads it (asynchronous)It identifies the OTA from the sender and display name, checks whether it's a cancellation, and pulls the booking number out of the HTML or quoted-printable body.Parse failure: alert email over SES
  6. The order is marked as cancellingThrough the platform's order API, with no one opening the email.

Design decisions

  • Per-team addresses instead of one shared inbox. Routing and source checks come for free: mail to an address that doesn't belong to a team never gets parsed.
  • Drop invalid mail silently. Mail to an unknown address is discarded; we chose not to bounce it.
  • Store before parsing. Every raw email stays in S3, so there's always an original to check when a parse goes wrong.
  • One parser per OTA, several templates each. Detection by sender and display name (some OTAs send from generic addresses), HTML parsing with cheerio, and multi-language handling for the four markets.
  • Make failures visible. Parse failures send an alert email; a Python tool exports the emails in a time range to CSV when something needs investigating.

Results

The pipeline has run in production for over a year, handling up to 35k emails a month. To build realistic test data, I worked with Ops to get the OTAs to forward old mail and recovered about 3,200 of roughly 3,600 historical cancellation emails.
